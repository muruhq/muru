## 19.1 Decisions taken

| Decision | Choice |
| --- | --- |
| Name and binaries | Project muru. One binary muructl with daemon and edge subcommands. Runtime library distribution and import name muru |
| Process layout | Separate edge processes from the daemon in production, embedded in one process in development. Both built as libraries |
| Edge to worker protocol | Own framing with protobuf payloads over Unix sockets, one request per pooled connection (ADR 0021, superseding ADR 0001). gRPC remains for the control plane and admin API |
| Worker link server | Rust inside the extension, started after fork. No grpcio anywhere in the worker |
| Application threads | A fixed pool of long-lived threads with persistent Python thread states, each request in a fresh contextvars context (ADR 0022) |
| WSGI and ASGI in one worker | Requests handed across per request in either direction: the muru.wsgi_to_asgi environ key and the asgi_to_wsgi scope extension, with lifespan registration and a WebSocket adapter under muru.asgi, each direction enabled by a handoff setting (ADR 0023, ADR 0042) |
| Counting requests in a worker with both interfaces | The side that runs a request counts it: threads for WSGI, the event loop's concurrency for ASGI, whichever the default mount is, with a detected interface resolved once and used everywhere after start-up (ADR 0048) |
| Preload | auto by default everywhere: preload with an import check, falling back to per-worker imports when the import left sockets, threads, child processes or event loops behind (sections 6.1 and 6.2) |
| Releases | Immutable. Configuration changes are new releases |
| Provisioning | One procedure, muructl build, called by muructl run, the daemon's Building state and the image build stage. Install from locks, never resolve. One knob, build.when: auto builds what is missing and leaves what exists alone, always builds on every start and lock change, never builds nothing; the same key in development and under the daemon. A missing interpreter is installed only where an environment would be built (ADR 0036) |
| Environment builds | Development builds the project's own .venv with the developer's uv, as uv sync would; the daemon builds into STATE/envs/APP/RELEASE as the release's user with --no-dev and no source builds. Building needs pyproject.toml, uv.lock and uv; a machine without uv runs on an existing environment and is told how to get uv (section 8.2) |
| uv | External program, optional muructl[uv] extra. Development uses the developer's uv as it is; the daemon isolates its directories but keeps the project's own [tool.uv] configuration, passing UV_CONFIG_FILE rather than UV_NO_CONFIG for builds (ADR 0036) |
| Garbage collection | Measured in every worker through gc.callbacks, on by default with no setting, since the callback costs far less than the shortest collection; the generation label is what the interpreter reports, full on free-threaded builds. Muru does not yet decide when collection runs (ADR 0038) |
| Runtime library | Provided by muructl on the host's PYTHONPATH in every mode, one directory per interpreter tag, fetched as a wheel and unpacked without pip or uv; never a required application dependency. A matching copy already in the environment is used as it is and nothing is fetched, so offline machines need no flag (ADR 0037) |
| Python versions | CPython 3.11 and later, free-threaded from 3.14t |
| Platforms | Linux for production, macOS for development, no Windows |
| wsgi.input_terminated | Always True. chunked_body defaults to buffer |
| wsgi.multiprocess | True for daemon-managed releases, False for single-process development runs |
| Body size limit | 10 MB by default, as in mod_wsgi-express. Routes that accept larger bodies raise it explicitly |
| Containers | Host and workers in the container, daemon and edge outside; muructl is PID 1 with a built-in init and the host is a subreaper under it, so no tini (ADR 0035) |
| Muru in an image | Built in when the image is built: muructl installed from the PyPI wheels with uv tool install, the runtime library fetched by the build stage for the image's interpreter; no static binary, no muructl image, no bundle injected at deployment and no official base images (ADR 0046) |
| Error override | Off by default |
| Reload | Off by default. Every reload is a new release |
| Licence | Apache-2.0 |
| Order of interfaces | Prove the architecture with WSGI first (phases 0 and 1). ASGI, including lifespan and WebSockets, follows in phase 2 |
| Repository and registry | github.com/muruhq/muru, with container images on ghcr.io/muruhq |
| Dashboard | Server-rendered askama templates with htmx, Server-Sent Events and uPlot, via the JSON gateway. Built with cargo only. Minimal read-only version in muructl run from phase 1. Shows and never changes, in every mode; control is muructl's (ADR 0060) |
| Development toolbar | Inserted by the edge into HTML pages of a development run, opt-in with --toolbar, its files and data at the reserved prefix /_muru/ on the application's origin; Server-Timing and Muru-Request-Link on every response of a development run; nothing of it under --allow-public, muructl serve or the daemon (ADR 0062). Panels are data in the request record drawn by minijinja templates and sanitised, the built-in panels included, with no panel JavaScript (ADR 0063) |
| Managed HTTP server releases | In scope for migration cutovers in phase 3: fixed instances, server profiles, full traffic management, no Python-specific features (section 9.9) |
| Free-threading | Supported from phase 1 with the WSGI bridge, with the extension designed for it from the outset (section 6.11) |
| Runtime wheels | Version-specific wheels for every supported CPython, regular and free-threaded. No abi3 |
| gRPC mounts and authentication sub-requests | In initial scope, phase 3 (sections 6.13 and 4.16) |
| TLS cryptography | rustls, tokio-rustls and rcgen on the ring provider in every crate; aws-lc-rs banned by cargo-deny so cmake never becomes a prerequisite (ADR 0024) |
| Retries | A request is sent again only when no worker has read it: a worker that cannot be connected to or closes its connection before the head is written is skipped for another. Nothing is sent again after a worker has read the head, whatever the method (ADR 0032) |
| Worker liveness | Native, in every worker: a thread attaches to the interpreter every 500 ms and the worker reports to its host every second; either quiet for gil_stall_timeout (30 s) replaces the worker as the hard timeout does. HTTP liveness probes stay opt-in for application failures (ADR 0031) |
| Worker group routing | A group's `match` takes `client_class`, `host` and `method` lists, never headers, which are a client class; groups rank by how many lists they give, then by prefix length. An optional group's requests wait as for a group at zero workers and never fall through to the default group. A group's `mounts` subset is served by its workers but imported by the host, with the default mount always served (ADR 0033) |
| Coding agents | An MCP server in muructl (`muructl mcp serve`, stdio, rmcp) whose tools run muructl's own commands with `--json`, so every result has the shape the CLI prints; task-shaped tools, `--read-only` and `--allow` enforced by the server, local only until the TCP admin listener (section 10.11, ADR 0039) |
| Commands | Declared by the application under `[tool.muru.commands]`, fixed with the release, with checked inputs (secret ones only in the environment, and over MCP only as secret store references); run by the daemon with the settings it starts the release's host with, streamed through the admin API, ended with their caller; `muructl exec` for one-off commands; with no application named, the same commands run for the project in the current directory, through a `muructl run` or `muructl serve` of it or by muructl itself (section 9.12, ADRs 0040, 0041 and 0050) |
| One application in a container | `muructl serve`: controller and edge in one process with the host and workers as children, one release, nothing persistent; configuration from defaults, `[tool.muru]` and its serve table, `MURU_SERVE_*` variables and flags, highest last, with `--config` or `MURU_SERVE_CONFIG` naming a project settings file read in place of the one beside the code; one writable run directory; no installs at run time; probes and metrics on an admin port open by default, status opt-in, control only over the socket (section 13.9, ADR 0044) |
| A container's limits | Nothing is sized from cgroup v2 limits: `--processes` defaults to 1 and a hard limit is only the user's; the limits are read when used, at every memory check, reported, and warned against when the configuration does not fit; a memory guard replaces the largest worker, one at a time, while less than the headroom (10 %, at least 128 MiB) is left under `memory.max`, under serve and the daemon alike (sections 7.7 and 13.9, ADR 0061) |
| Times on log lines | Always recorded, shown by output: full UTC (RFC 3339, milliseconds, `Z`) in files, JSON and `muructl logs`; none in front of application lines on standard output, where a terminal, a container runtime or journald has its own, with `--timestamps` to add it; access lines keep their time, a short local clock only on a terminal (section 11.8, ADR 0043) |
| Levels of a request's settings | A virtual host's settings are its site's defaults: a setting is the first set of the route, the mount, worker group and release that serve the request, the virtual host, the node and the default, as error pages were. What the edge applies before it knows the host, the proxy settings and the limits on the request head, belongs to the listener and the node, not to a host (sections 3.3, 4.3, 4.6 and 4.7, ADR 0049) |
| Whose configuration a name means | `--config` is taken only by the commands of one mode: the daemon's file where a daemon is started, and on `muructl serve` and a project's commands a project settings file read in place of the one beside the code, in the form of a muru.toml with serve's settings under `[serve]`; the variables carry the mode, `MURU_DAEMON_CONFIG` and `MURU_SERVE_CONFIG`; `--print-config` shows a command's own resolved settings with their sources; a deployment file beside code is `muru.deploy.toml` (ADR 0079, in place of `muru.daemon.toml`); a muru.toml stands in place of `[tool.muru]`, never merged (sections 13.1, 13.8 and 13.9, ADR 0051) |
| Writing a release as a file | `muructl render` writes the release a command line describes as a table of the daemon's format, from the flags, the source's settings and the defaults, with no daemon; the flags about the act of deploying (`--hold`, `--no-wait`, `--retain`, `--retain-workers`) are `muructl apply`'s, for every release it adds; `muructl deploy --dry-run` plans one deploy; `deployment export` writes a recorded release whole (section 10.4, ADR 0052) |
| The release that serves, in files | An application's `serving` key names its serving release, declared or recorded: the apply holds the other releases it adds and promotes a recorded one after writing the routes; without it an apply that adds one release gives it the traffic and one that adds several is refused (ADR 0082); a rollout under way keeps the traffic, and the key may name only its baseline or candidate meanwhile; `--prune` needs the serving release declared; export writes the key (section 10.4, ADR 0054) |
| An atomic apply | An apply prepares, then commits: it creates the applications and starts the releases it adds held, removing them all again if one does not start, then writes the hosts, routes, overlays, client classes, rate limits, access logs and promotions in one transaction and gives the edge one snapshot; `--prune`'s releases and applications go after it; `--no-wait` answers once the releases are recorded; applies happen one after another, a second waiting for the one under way (section 10.10, ADR 0055) |
| Three kinds of configuration | A project's settings, the daemon's configuration and deployments each have one home and one way to change them, and each reader refuses the others' tables: the daemon's file never holds an application, an apply never configures the daemon, and client classes, rate limits and conditions are the one overlap, a name defined once; `muructl daemon config` for the daemon's file, `muructl deployment` in place of `muructl config`, `muru.deploy.toml` in place of `muru.daemon.toml`, and `muructl render` with a required `--release` (sections 10.3 and 10.4, ADR 0079) |
| Named deployments | A `deployment` key names a set of objects applied, pruned and removed together, with `default` for files without one and for what commands make; names stay node-wide, only the owner changes or removes its objects, nothing is removed while another deployment names it, `--prune` reaches the deployments the files name and `--prune=all` every one (section 10.13, ADR 0080) |
| Files applied at start | `--apply` on `muructl daemon start`, `run` and `up` applies at every start, and to a daemon already running; with nothing running the daemon restores what the store holds and then applies; a failed start apply fails the start, leaving what served detached; `muructl daemon reset` puts a node back to nothing with everything stopped (section 13.13, ADR 0081) |
| Files and commands on one application | An application is the files' or the command line's; a deploy on a declared one warns; a `serving` key is the file's, an apply never undoes a rollback on its own and says when it reverts another move by command; a release kept in files is removed through them, a prune never takes the serving or the rollback release, and an application's own settings are declared in one file (sections 10.4 and 10.13, ADR 0082) |
| Capping a group | `cap_workers` in an overlay or a schedule caps a group; the lowest cap applies and wins over every floor, with apply warning of a floor above a cap, the excess drains at once outside the churn budget, a pin stands over it, and `muructl scale --cap` makes its own overlay `APP:cap` (section 7.5, ADR 0065) |
| Deferring imports | `lazy_imports = true` installs unwrapt's deferral through a module of Muru's own at the head of the instrumentation list, ahead of tracing's, with the configuration unwrapt finds itself; it stays through the fork, the host logs at the fork what was deferred and used anyway, and the workers mark the loads that resolved a deferral; the release record keeps it as a flag (section 6.17, ADR 0066) |
| The import report | `import_report = true` records the host's load with unwrapt's profile recorder, each import labelled with the target being loaded; at `load_finished` the host analyses it, adding who pays, the import check's findings and advice written as configuration, and sends it in parts to the controller, which keeps it in the daemon's store beside the release or in a run's memory; `muructl debug imports` reads it with the workers' loads since the fork (section 6.18, ADR 0067) |
| Development behind a daemon | A detour: `muructl detour run` holds a release of kind `detour` open on a local user daemon with a streaming admin call, reached by the daemon's edge over HTTP on the run's Unix socket (`h2c` for gRPC, `http1` otherwise), preview only by default and more traffic by a runtime overlay it owns; a daemon setting off by default and refused on a system daemon (ADR 0075, section 9.13) |
| Deployment settings | On the application: variables, secrets by reference, worker counts, recycling, the host's timeouts and the memory policy, set by `muructl app set` or `[app.NAME]` and taken by every later release under its own flags and over `[tool.muru]`; a deploy takes nothing from the release before it (ADR 0076, section 3.3) |
| Sockets and runtime files | The runtime location holds sockets and nothing else, since macOS deletes regular files under `/tmp` by age: every regular file a running instance keeps is in `run` under the state directory, the registry in the account's state location, and a host's sockets in a directory named by its release's number, so no socket's path carries a name and the longest is 30 bytes below the run directory; the run directory is locked on itself; nothing is carried over from the layout before (ADR 0083, section 13.8) |
| Previewing a release | Every preview is the release's ID and a preview secret of its own, `RELEASE.SECRET` in the header or the cookie, never the ID alone: the secret is made with the release and kept in the store, given out only by `muructl preview` as a one-time entry link or the header, taken off every request before it is passed on, and changed by `--new-secret`; every preview that misses is answered alike; upstreams are not previewed (ADR 0084, section 4.22) |
| Swapping workers | `max_surge` (1) and `max_unavailable` (0) for each release and group, enforced at two levels: the host paces the swaps inside a release, voluntary ones through one queue per group and involuntary ones at once but in the same order, and the rollout engine paces moves between releases; the node's budget holds each group's surge allowance, with none for a release that takes no traffic; `RestartRelease` restarts every worker of a release through the queue; a changed setting is a new release, with no in-place restart; stopping the old release before starting the new is a manual procedure, not a strategy; a node with no memory limit gets a warning from `muructl doctor` and no default (sections 7.8, 7.9, 9.15, 10.5 and 10.14, ADR 0085) |
| The count a release starts with | `muructl deploy --initial-processes` gives the count a release starts with, apart from its `processes`: the budget checks the deploy at it, a release with no share of traffic stays at it, and once it serves it takes its declared count or what its scaling policy says, admitted by the budget as a scale-up (section 7.10, ADR 0086) |
| Rollouts that share capacity | `muructl rollout canary --capacity shared`: the baseline and the candidate share the baseline's worker count, each sized by its share of the traffic with one worker at least, through pins of the rollout's own; a step grows the candidate, moves the traffic and drains the baseline, or with no room in the budget has the baseline give up `max_unavailable` workers at a time first; a step ends when the baseline has drained; a rollback grows the baseline back without waiting; managed HTTP server releases are refused (section 9.16, ADRs 0085 and 0087) |
| Events a host raises | A supervisor acknowledges a host's events by a cumulative number once each is recorded; the host holds what is not acknowledged, at most 256, and sends it to the supervisor that connects next, and the daemon keeps the last number recorded in the state store, so every event is recorded once (ADR 0088, issue 982) |
| A worker that stops | A worker told to stop writes STOPPING on each link connection before closing it and starts no request from then on; the edge sends a request answered that way once more, on a new connection, when all of it is still at the edge, so a worker replaced with no daemon to tell the edge costs no request (sections 4.8 and 5.3, ADR 0089, issue 986) |
| Supervising a managed server's instances | One `restart` table, shared key for key with the services to come: `always` by default, a wait doubling from 1 s to 1 min, and no giving up unless `give_up_after` says so, with a crash loop made loud instead (the `backoff` state, server.crash_looping at the third quick exit in a row, muru_server_exits_total); a release restored at the daemon's start is tried again with the same waits while a deploy fails at once; and `muructl restart --all` restarts the instances one at a time through the supervisor, each answering its readiness probe before the next (section 9.9, ADR 0090, issue 393) |
| Services | Muru supervises the processes that belong beside the applications it serves and no others: a node's services, declared as `[service.NAME]` in applied files and kept in the store, run by the supervisor and the restart policy managed servers have, with `muructl service` to list, show, start, stop, restart and signal them, a log each, and adoption across daemon restarts; a stop by hand is held until a start, a changed definition restarts on apply, and an instance is chosen with `--index` (section 9.17, ADR 0091, issues 484 to 487) |

## 19.2 Open questions

1. Resolved by ADR 0021: the phase 0 benchmarks put gRPC 24 to 37 percent behind mod_wsgi daemon mode on hello world and the framed link ahead of it, so the framed link replaced gRPC on the edge-to-worker link (section 5.1).
2. Retention defaults for warm superseded releases on memory-constrained nodes. Provisional choice, to review later: 30 minute retention, scaled down to the host plus one worker per group, dropping to host only and then stopping under memory pressure (section 9.1). After a deploy, the previous release is kept running with no traffic for a retention window (30 minutes by default, section 9.1) so a rollback is instant. That costs the old release's full memory for the whole window. The question is whether the default should stay at 30 minutes, become shorter, or be decided automatically from free memory, for example keeping the old release warm only while the node is under its memory budget and stopping it otherwise (rollback would then need a cold start).

## 19.3 Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Link overhead for small requests | Throughput below alternatives | Retired: the framed link measured at the level of mod_wsgi embedded mode and gunicorn per request (ADR 0021). Coalescing stays |
| GIL contention in the bridge | Lower throughput per worker | Environ built in Rust, GIL released while blocking, batched event delivery, early measurement |
| Runtime wheel matrix | Build and test burden | One build path for all versions in the release workflow, CI matrix limits, new Python versions added as soon as their release candidates appear |
| Preload incompatibilities | Applications break after fork | Import check with automatic fallback to per-worker imports, post_fork hooks, explicit preload settings, clear diagnostics |
| Sticky sessions keeping old releases alive | Slow drains | sticky_grace, drain deadlines |
| Shared state between overlapping releases | Data errors during deploys | Documentation, migration guidance, muructl exec |
| Soft timeout limits | Exceptions not delivered or swallowed | Opt-in, BaseException subclass, hard timeout backstop |
| Event loop starvation in mixed mounts | WebSocket latency | Loop lag signal, per-mount pools, moving mounts to groups |
| Autoscaler instability | Churn or under-provisioning | Sustain windows, asymmetric cooldowns, churn budgets, advisory mode, schedules |
| Root daemon | High-value target | Small privileged surface, no client parsing, capabilities dropped |
| HTTP/3 and ACME maturity | Delayed features | Deferred to phase 4, TLS termination upstream as a workaround |
| Platform differences | macOS behaviour differs | Linux-only production, documented degradations |
| Scope growth | Delays to 1.0 | Phases with exit criteria, future ideas kept out of scope until decided |
