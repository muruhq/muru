Muru reports three kinds of data: metrics for continuous measurements, logs for per-request and application output, and events for changes of state. Each has one source of truth and several consumers.

## 11.1 Metrics

Prometheus metrics are served by the daemon on the admin listener (/metrics on the JSON gateway) and, optionally, on a dedicated metrics listener bound to an internal address, never on public listeners by default. Each edge process reports its metrics to the daemon, which aggregates them, so one scrape covers a node. Names use the muru_ prefix and labels app, release, group, mount, route and host where relevant.

| Area | Examples |
| --- | --- |
| Requests | muru_requests_total by status class and reason, muru_request_duration_seconds histograms (queue, application, total), muru_requests_in_flight, muru_request_retries_total, muru_access_log_dropped_total, muru_auth_requests_total by result |
| Capacity | muru_queue_depth, muru_slots_busy and muru_slots_total (each by side, `threads` or `loop`, since a request is held against the side that runs it, section 5.1), muru_capacity_utilisation (busy slots over slots of the busier side, sampled every second and averaged over 30 s, the saturation signal for an autoscaler such as an HPA or KEDA, since CPU stays low while an I/O-bound application's slots are full), muru_websocket_connections, muru_websockets_closed_total by side and how, muru_websocket_duration_seconds; muru_handoffs_total by the interface a request was handed to (section 6.14) |
| Workers | muru_worker_requests_total and muru_worker_requests_in_flight as each worker last reported, muru_worker_sync_threads_busy and muru_worker_sync_threads for a worker with an event loop (the busy threads and the size of each pool synchronous code runs on, by pool: loop, anyio or asgiref, section 6.6), muru_worker_cpu_seconds_total, muru_worker_memory_bytes by kind (uss, pss, rss), muru_gil_wait_seconds, muru_loop_lag_seconds and muru_handoff_queue_wait_seconds histograms, muru_worker_recycles_total by reason, muru_worker_exits_total by reason |
| Garbage collection | muru_gc_collections_total, muru_gc_seconds_total and muru_gc_collected_objects_total by generation, muru_gc_pause_seconds histogram by generation and by whether requests were in flight |
| Scaling | muru_scaling_decisions_total, muru_workers_desired, muru_workers_ready, muru_churn_reaps_total |
| Edge | muru_connections_open, muru_connections_refused_total, muru_tls_handshakes_total by result, muru_snapshot_version, muru_upstream_health |
| Bodies and uploads | muru_upload_spool_bytes |
| Clients | muru_requests_total by client_class, muru_rate_limited_total by limit, client class and action |

**Garbage collection.** CPython's cyclic collector pauses the whole process while it runs: on a regular build the collecting thread holds the GIL, on a free-threaded build the collector stops every thread. The gc.freeze() sequence of section 6.2 keeps the preloaded heap out of a worker's collections, and what remains is measured rather than guessed at. Each worker's runtime registers a `gc.callbacks` entry that notes the time and the requests in flight when a collection starts and, when it stops, records the pause, the generation and the objects freed, keeping pauses with requests in flight apart from pauses that cost nothing. The figures travel with the worker's status line, as its CPU time and GIL waits do, and are exported for each worker: counters of collections, time collecting and objects freed by generation, and a histogram of pauses by generation and by `requests` (`in_flight` or `none`) over the signal bounds of section 7.3. The generation label is what the interpreter reports: `0`, `1` or `2` on a build with generations, `full` on a free-threaded build, whose collector takes the whole heap each time. `muructl debug memory` and the dashboard's worker view show the same figures beside the gc counts (section 11.7), and the scaling diagnosis names collection when it takes a tenth of the workers' time or more (section 7.3). The callback costs two calls into the extension, a monotonic clock read and a few atomic additions per collection, about a microsecond against the tens of microseconds or more an automatic collection takes, so it is on in every worker with no setting (ADR 0038).

Some figures are read from a family above rather than exported again: the queue wait is the `queue` phase of muru_request_duration_seconds, a worker's CPU ratio is `rate()` over muru_worker_cpu_seconds_total, and bodies refused for their size are muru_requests_total with the `body_too_large` reason, so there is no muru_queue_wait_seconds, muru_worker_cpu_ratio or muru_body_rejections_total. The edge's own CPU time per thread is not exported.

The dashboard reads the same values from in-memory history. OTLP metric export is optional.

## 11.2 Access logs and application logs

- Access logs are structured (JSON by default, or a configurable text format) with request id, host, route, release, group, worker, snapshot version, status and reason, bytes, and timings for queue, application and total, plus internal redirect hops.
- **The format and the file.** `access_log_format` in `[logs]` and on a virtual host is `json`, one object a line, or `combined`, the combined log format of Apache and nginx; a host's replaces the node's for its records. A host's `access_log_file` names a file in the daemon's log directory that takes its records in place of `access.log`: a plain name, not one of the daemon's own, and hosts that share one give the same format. Both travel on the host's access log choice in the snapshot, the file as a path, so an apply or a reload changes them without a restart. The edge's writer thread opens such a file when a line first wants it and again after a reopen, and the daemon rotates it with `access.log`. A combined line has the client, the UTC time, the request line, the status, the bytes sent, the Referer and the User-Agent, which a record keeps only while some record is written in that format; the identity and user fields are hyphens, and a WebSocket has its handshake's line alone. Every JSON record names its virtual host as `virtual_host`, the host's configured name, which is how `muructl logs --access --host NAME` picks a host's records out of `access.log` when the host names no file; with a file it reads that, printing a text format as written. A format template with named fields is not offered (section 20.14).
- Which records are written is a filter apart from where they go: on, errors (4xx and 5xx responses, requests at least a slow threshold, and WebSockets that closed other than normally or going away) or off, less path patterns left out. Every record is counted in the metrics and kept in the in-memory ring whatever the filter says. Under the daemon the `[logs]` table sets the node's filter, and a virtual host's table and an application's table may each set their own, the application's laid over its host's and the host's over the node's key by key with the excluded paths adding up (ADR 0049); a request the edge answers before an application is chosen is written by its host's. All travel in the snapshot, so `muructl daemon reload` and `muructl apply` change what the running edge writes without a restart. A development run and `muructl serve` take theirs from their flags and tables.
- `muructl logging access MODE [--app APP] [--path PATTERN]... --for DURATION` changes what is written for a period and reverts on its own, as `muructl logging level` does for loggers (section 11.4). A change covers one application or every one, and the paths matching its patterns or every path; the newest in force that covers a request decides, with the slow threshold of the filter it replaces, and one that names paths writes them even where the filter excludes them. The daemon keeps the changes in memory and sends those in force in every snapshot, each with its end, which the edge honours without being told, so a change cannot outlast its period and a daemon that starts again has none; it records access_log.changed and access_log.reverted. A development run and `muructl serve` change their own edge's filters through the admin socket and print the same events. `--reset` puts the changes back, and the command without a mode lists those in force with the time each has left.
- Worker stdout and stderr are per-worker pipes. The host creates them at fork and passes the read ends to the daemon over the control socket. The log collector tags lines with application, release, group, worker and stream, keeps ring buffers for the CLI and dashboard, and writes sinks. Workers are line-buffered. In development mode there is no collector yet, so the host itself relays the pipes to its standard error, each line tagged with the worker's index and, for stdout, the stream (muru.worker[0]: and muru.worker[0].stdout:).
- Sinks: terminal (development), journald (default under systemd), files.

## 11.3 Log rotation

- Writer threads in long-lived processes own every file, so rotation is a handle swap and never involves workers or restarts. Files use O_APPEND, so concurrent edge writers during handoff never interleave within a line.
- Built-in rotation: size and time based, retention count and age, configurable backup names, background compression (gzip or zstd). The rotator compares the period each file was last seen in with the current one, and keeps that record per file in the state store (section 10.2), written before it rotates, so a period that ended while the daemon was stopped rotates a file once at the daemon's next check and a further restart does not rotate it again. The record is the signal because a file's own times are not one: its birth time is not available on every platform and file system, and its modification time keeps moving under an edge and hosts that keep serving and writing while a daemon is stopped. A file with no record only notes its period, and an empty file is not rotated. The edge reopens the access log, the files virtual hosts name and its own edge.log on SIGUSR1: the daemon gives it edge.log's path, and it opens that path again with O_APPEND and puts it on its standard output and error with dup2, as a host does its release log, so edge.log is renamed and reopened like the others. Only a managed HTTP server's log is rotated in place (section 9.9), losing the lines written while it is copied.
- External rotation: one rule covers every log Muru writes, so one logrotate entry for `*.log` and `apps/*/*.log` needs no per-file exception. logrotate renames the files; each writer opens its file again by name, the edge the access log, the hosts' files and edge.log, each host its release log, a background daemon daemon.log, either when muructl logs reopen (or SIGUSR1 to the daemon) asks or, with `[logs] reopen_on_rename` (true by default), when the daemon notices the rename itself. Under the daemon only, the controller stats each path its writers can reopen (the access log, the hosts' files, edge.log, daemon.log when it writes one, every running release's log except a managed server's) every 5 seconds and once at start, and when a path no longer leads to the file last seen there (another device and inode, or nothing) it reopens every writer as muructl logs reopen does, with a logs.reopened event naming what was renamed. It keeps the file last seen at each path in the state store (log_files_seen), so a rename made while it was stopped is noticed at the first check, and it forgets them after every reopen it causes, by its own rotation, a truncation's swap or a reopen asked for, so that what its writers open next is noted rather than taken for a rename. Plain stat polling behaves the same on Linux and macOS; inotify and kqueue would notice sooner, but the few seconds cost nothing once logrotate is given delaycompress, which keeps the renamed file whole until the reopen. Files an application opens itself still need a postrotate running muructl logs reopen --workers. A development run writes one file at most, its access log with --access-log-file: muructl logs reopen against the run, or SIGUSR1 to its muructl process, reopens it with the same AccessLog::reopen the edge process uses, off the runtime, and without one both say there is nothing to reopen rather than end the run; --workers is refused there, since SIGUSR1 to a worker runs its hook directly. reopen_on_rename does not apply to a run. A managed HTTP server's instances write their file directly and cannot reopen it, so with external rotation those files keep logrotate's copytruncate, which can lose lines, until the log relay reaches them. rotate = 'external' disables built-in rotation, and configurations where both would rotate a file are rejected.
- Listing logs: muructl logs list reports each log with its size, archives and total, and with --archives each archive on a line of its own under its log, oldest first, with its size and modification time, as the live file has one too. An application, APP@RELEASE, --access or --host HOST narrows the list, and its total, to those logs, and a target with no log is refused; the narrowing is muructl's, on the whole list the daemon or the files give. A log is one of the files the daemon writes (access.log, edge.log, daemon.log), a file virtual hosts name for their records, or a release's output under apps/APP/RELEASE.log, and an archive is a file whose name is the log's with a stamp or number and optionally a compression suffix. A log is orphaned when the state store no longer has its release or names no virtual host for its file. A command on the log files goes through the running daemon, and with none listening it works on the files themselves, taking the daemon's location options; the state store, opened read-only and so never migrated by these commands, supplies what exists when it can be opened.
- The daemon's own logs: muructl logs --edge and --daemon show or follow edge.log and daemon.log as muructl logs does a release's output. A development run and muructl serve write no log files, so their TailLogs refuses both.
- Reading logs with no daemon: muructl logs goes through TailLogs to whatever answers at the admin socket, and when it finds no daemon listening and no socket was named it reads the file in the log directory itself, with the same --follow, --lines, --no-timestamps and --json, since a daemon that failed to start can say why only in daemon.log and a stopped daemon's last requests and output are worth reading. APP@RELEASE, --access, --edge and --daemon need only the log directory; an application named alone and --access --host HOST need the state store, opened read-only as the other commands on the log files open it, for the current release and for where the host's records are, and say so when it is not there.
- Truncating a live log: muructl logs truncate cuts a log to its newest content, at a line boundary. Writers open their files with O_APPEND, so keeping nothing truncates the file in place, which needs no free disk space. Any other size writes the kept part to a new file with the old file's mode and owner, renames it over the log, has the writers reopen, and appends what the old file gained during the swap, so no lines are lost and a few can land out of order. Writers that cannot be told to reopen (the instances of a managed HTTP server) are cut in place instead: the kept part is written aside, the file truncated and the kept part appended, and lines written while it is copied are lost. With no daemon running every log is cut in place, because an edge or a host a detached daemon left running may still have it open. A running daemon holds the files against rotation for the duration of the cut.
- Rotating on demand: muructl logs rotate runs the rotator now for named logs, or for every log with content except orphaned ones, keeping the policy's compression and count. Under a daemon it is a rename and a reopen like any rotation, with the same exceptions cut in place. A second rotation within one second takes the next second's stamp, so it cannot replace the first's archive. With rotate = 'external' it is refused, as is any configuration in which two things would rotate a file. With no daemon running every log is rotated in place, as for truncation, and compression finishes before the command exits.
- Pruning: muructl logs prune removes archives by the newest N per log or by age, and with --orphaned the logs and archives of what no longer exists, each by the same question as truncate, with --yes and --dry-run. A running daemon reads the store again after listing the files, so a log whose release was just created is not taken for an orphan, and removes an application's directory once it is empty. With no daemon --orphaned needs the state store to be available.
- Applications that open their own log files get an on_reopen_logs control message (muructl logs reopen --workers), whose default hook makes logging file handlers reopen on next emit.
- A log that cannot be written never stops what serves: the host's relay writes a worker's lines to its standard error in one write each time, and a write that fails (a full disk under the release's log, say) drops those lines and counts them, the count reported as one of the host's own lines once a write succeeds again. The bytes are written to the descriptor directly rather than through a buffered stream, which would keep what failed and write it later.
- Under muructl run and muructl serve, muructl relays the host's standard output and error to its own. The relay tasks hand each line to a writer thread of muructl's over a bounded channel of 1024 lines and wait for room, and the thread gathers a stream's waiting lines into writes of up to 64 KiB. A terminal or a container runtime that stops reading therefore holds up that thread, and then the host's pipe, never a thread of muructl's runtime, which also carries the edge, the admin socket, the dashboard, the file watcher, the supervisor link and, under muructl serve, the probes. When a host stops or exits, muructl waits for its relays to reach the end of its output and for the thread to write it, so the host's last lines come before muructl's own.
- Backpressure never reaches requests: the access log drops and counts records when stalled; application output uses a large drop-oldest queue by default, or blocks if configured. The edge's access log lines go to a writer thread of their own over a bounded queue (16k lines), which gathers what is waiting into writes of up to 64 KiB and reopens the file in order with the lines; a request's task only queues its line, and a line that finds the queue full is dropped and counted in muru_access_log_dropped_total, the writer saying how many once it has caught up. The edge and a development run wait for the queue to empty before they exit.

## 11.4 Python logging defaults

- Before importing the application, the host sets the root logger level and replaces logging.lastResort with a platform handler using the configured format (a format string or json) that writes to stderr. A lastResort handler is used only when no handler exists in a logger's hierarchy, so basicConfig and dictConfig behave exactly as without Muru.
- Every record carries the request id and the Muru tags, through a record factory installed with the defaults, as `muru_request_id`, `muru_app`, `muru_release`, `muru_group` and `muru_worker`, so an application's own format can use them; the prefix keeps them apart from an application's `extra`, which `logging` refuses to let overwrite an attribute the record already has (OpenTelemetry's logging instrumentation prefixes its own the same way). The json format writes the request id as `request_id`. Optional: logging.captureWarnings and a per-logger level map.
- An exception the application did not catch (a WSGI or ASGI application, a gRPC handler, a response's close()) and one a hook raises is reported through `muru.logging` on the `muru` logger at ERROR with exc_info, as gunicorn does with `gunicorn.error`: it reaches the application's handlers when it configured some and the platform handler when it did not, and carries the request id the bridge set, so under the json format it joins its access log record. Whether the record would be shown is decided as `Logger.callHandlers` decides, filters aside: when the logger is disabled (a dictConfig with disable_existing_loggers after the logger existed), a level above ERROR is in force on it, its ancestors or `logging.disable`, or the only handlers on its way up take no ERROR or are NullHandlers, the traceback is written to standard error after a `muru:` line naming what raised it, so a logging setting never loses it. A filter that drops the record is the application's choice and is honoured.
- Precedence: Python default, daemon configuration, application, release, the application's own configuration, then time-limited runtime overrides (muructl logging level RELEASE --logger NAME --level DEBUG --for 15m).
- **Layers, settled by the implementation.** The table is `logging.python` with `level`, `format`, `capture_warnings`, `loggers` and `warnings`, at three layers: the daemon's `[logging.python]` in its own file, the application's `[tool.muru.logging.python]` in its source, and a declared release's `logging.python`. They merge key by key, a more specific layer's key winning, `loggers` by logger name and `warnings` adding up with the more specific layer's after the others. The application's and the release's are merged when the release is created and each key's layer recorded; the daemon's is read when a host starts and laid under them then, since the defaults are installed before the application is imported, so a running host keeps what it started with and a reload reaches each application at its next restart or deploy, which the reload's message says. `config show --effective` lists each key of each release with its layer, `daemon configuration`, `[tool.muru]` or `the release table`. `muructl run` and `muructl serve` read no daemon file and take the application's table alone.
- **Warnings filters.** `warnings` is a list in the syntax of Python's -W option (`action:message:category:module:lineno`), applied with `warnings.filterwarnings` in order before the application is imported, so a later filter, and so a more specific layer's, takes precedence as a later -W option does; the message and module match literally from the start, as -W reads them. The syntax is checked when the configuration is read, naming the entry; the category is imported only when the host applies the filter, and one that cannot be is left out with a host line saying so. An application's own `warnings` calls still win.
- MURU_LOG_LEVEL, MURU_LOG_FORMAT and muru.logging.default_config() let applications adopt the platform defaults explicitly.
- The standard format has no time, because Muru adds one where the output wants it (section 11.8); the json format carries the record's creation time in its `time` field.

## 11.5 Event stream

- One stream of state changes: configuration, releases and rollouts, host and worker lifecycle, recycles and timeout kills, scaling decisions, drains, schedules, edge and daemon upgrades, certificates and warnings.
- CloudEvents 1.0 JSON with a node-wide sequence number (muruseq), subject (app/release/group/worker), actor (user identity or component), correlation ids per rollout or deploy, and a level (info, notice, warning, error). Events never contain secrets or request data. Event types are listed in Appendix C.
- Pull: WatchEvents over gRPC, or Server-Sent Events on the JSON gateway, resumable from a sequence number. muructl events --follow uses the same stream.
- Push sinks with their own filters: webhooks (HMAC-signed, persistent outbox, at-least-once, deduplicate by id), OTLP log records (and spans for rollouts and deploys), journald or syslog, and JSON lines files.
- Retention: 7 days by default, capped by size. The audit log is the long-retained subset initiated through the API.
- A development run, and `muructl serve`, which have no state store, keep the events their hosts raise in memory for the life of the process, the last 256, across reloads, numbered from 1 as the daemon numbers its own and subject `app@rN` by the release that raised them; their admin socket answers ListEvents and WatchEvents from that ring, with `--after` and `--follow` as against the daemon (section 13.1).

## 11.6 Tracing

The edge creates a server span per request and forwards W3C traceparent and tracestate to the application in the request head, so OpenTelemetry instrumentation in the application continues the trace. Edge spans and optional worker spans (queue wait, dispatch) are exported over OTLP when configured. Rollouts and deploys can be exported as spans so they appear on the same timeline.

## 11.7 Debugging and live inspection

Every worker has a control connection to its host, and the host to the daemon, so the admin API can reach into any worker of any release: a laptop run, a release in a container, a worker under another user or, in phase 5, on another node. The `muructl debug` commands use that path to find out what a worker is doing and, when needed, to step into it. They share one shape: `muructl debug VERB TARGET [--worker N] [--for DURATION]`, where TARGET is a release or an application, the default is every worker of the release, and the output streams back over the same admin API stream it was requested on, so nothing opens a port.

**Two mechanisms.** Everything below is built on one of these.

- *From outside the process.* Python 3.14 added PEP 768, which lets another process read a running interpreter's frames and run code in it at a safe point; the sampling profiler (`python -m profiling.sampling`), `python -m asyncio ps` and pdb's remote attach are built on it. These need no cooperation from the worker and cost it nothing until used, so they work on a worker that is hung or spinning. The host is the agent: it is the parent, runs as the same user and in a container is PID 1, so it has the rights PEP 768 needs without anything being opened up. On interpreters before 3.14 these commands fall back to the in-process mechanism where one exists and are otherwise unavailable.
- *From inside the process.* A control thread in the runtime library, created by the extension and never holding the GIL while idle, that the host can ask to run named operations: sys.monitoring, tracemalloc, faulthandler, gc, importlib, logging. It stays responsive while the GIL is contended, because it is a Rust-side thread that attaches only to do its work.

**What a worker is doing now.**

- `muructl debug stacks`: the Python stack of every thread, with the request id, path and elapsed time of the request each application thread is serving, from the bridge's own bookkeeping. Taken from outside, so it works on a hung worker, with a faulthandler fallback when the interpreter cannot be read. Across a release the stacks are merged, so sixteen workers waiting on the same lock show as one stack with a count.
- `muructl requests`: the requests in flight now, from the edge, which sees every request including those no worker has yet (issue 379): counted by worker group, since the edge queues per group, as those queued for a slot, those holding a thread of the group's threads and those on an event loop, each with the age of the oldest, the columns of the sides the release has, with the same one-word headers as `debug status` for the same figures; and with `--list` each request, the oldest first by its start time, with its age, state (queued or running), kind as of now (`wsgi`, `asgi`, either with `streaming` once its head asked for immediate flushing, `grpc`, `handoff` once DETACH moved it across, `upstream` for a managed server; `-` while queued), worker, method and target, client and request id. An accepted WebSocket leaves the listing for `muructl websockets`, and a static file, answered at once, is never in it. The edge keeps the listing beside each request's access log record, registered when the record is made and removed when the request ends, spread over sixteen maps by a number of its own so that arrivals and ends do not serialise on one lock, and measured under load before it landed; what a request is charged to is what the edge charged (the worker's side from HELLO, moved by a handoff), which is what `debug status` shows from the worker's own table, so the two can differ for a worker serving both interfaces until the edge's accounting agrees (issue 362). Served by the daemon, a development run and `muructl serve` over the admin API (`ListRequests`), with `--json` and an MCP tool beside `websockets`.
- `muructl debug tasks`: for ASGI workers, the asyncio task tree with what each task awaits, from `asyncio ps` and `pstree`, and the event loop lag.
- Automatic capture: when a request passes its soft timeout (section 7.6), before a worker is killed for a hard timeout, and before a worker is recycled for memory (section 7.7), the host takes the stack dump first and attaches it to the event, so "worker killed after 60 s" reads "worker killed after 60 s, waiting in a database connect here".

**Profiling for a period.**

- `muructl debug profile --for 30s`: sampling with the standard library's profiler, of one worker or every worker of a release at once, written locally as collapsed stacks for a flame graph or as pstats. Safe on production, which is the point of sampling: at the default interval a profile costs a busy worker nothing measurable, whether read from outside (Linux, Python 3.15 and later) or taken by a thread of the worker, which with the GIL waits its turn for the interpreter and on a free-threaded build pauses the other threads for the moment each sample takes; at a 1 ms interval a busy worker loses a few percent (issue 374).
- `muructl debug trace --for 10s`: in-process sys.monitoring for exact call counts and times when sampling is too coarse. It costs the worker something, so it refuses a worker above a load threshold unless forced; the worker keeps serving while it runs, so the trace sees the requests it takes meanwhile.
- `--requests N --path PREFIX`: profile or trace only the next N requests matching a path or header rather than everything on a busy worker.

**Memory.**

- `muructl debug memory`: resident size, gc generation counts and the collections timed since the worker started (how many, how long, what they freed, and how many ran while requests were in flight, by generation; section 11.1) at any time, and object counts by type. With `--trace --for 30s`, tracemalloc for the period and the top allocation sites, or a snapshot diff between two points.
- Before a memory recycle (section 7.7) the host can take a snapshot of the worker it is about to replace, so the leak is attributed rather than just survived.

**Stepping in.**

- `muructl debug attach`: a pdb session in a worker, carried as a byte stream over the admin API. The worker is drained and pinned while the session lasts, its timeouts are suspended, the thread being debugged stays off the pool, and a maximum session length ends a forgotten session. With `--dap` the same tunnel carries the Debug Adapter Protocol for debugpy, so an IDE attaches through muructl rather than through a port.
- `breakpoint()` in application code: the runtime library's breakpoint hook waits for a `muructl debug attach`, raising an event that names the worker, file and line, and gives up after a timeout. Outside Muru the hook does nothing special, so the call is safe to leave in.
- `muructl debug exec -- CODE`: run a snippet in a worker and return its output. Admin role, audited, and off in production unless enabled.

**State and configuration.**

- `muructl debug inspect`: the worker's sys.path, loaded modules with versions and file paths, environment, resolved settings, open descriptors and sockets, and thread names. The environment names every variable and gives values only for those Muru sets (`MURU_*`), the interpreter's (`PATH`, `VIRTUAL_ENV`, `LANG`, `TZ`, `PYTHON*`, `LC_*`) and the release's own, from `[tool.muru.env]` and `deploy --env`, a secret store's value excepted (a secret as a file shows its `NAME_FILE`); the host names the release's in `MURU_DECLARED_ENV`, and the runtime library holds the list of the others in one place. `--env` gives every value, for a person at a terminal; the MCP `debug` tool never passes it (section 10.11). Every value shown has secrets redacted (the value of a key with SECRET, TOKEN, PASSWORD, PASSWD, KEY, CREDENTIAL or AUTH in its name or ending in _DSN, and the password of a URL under any other key).
- `muructl logging level` (section 11.4) changes a logger's level for a period and reverts on its own. With no level and no `--reset` it changes nothing and lists, for each worker, the loggers changed this way with the level set, the level it replaced and when it reverts (`until_unix_ms`, null until a reset), through the `logging` debug operation with `list`. Each worker holds its own changes, so a worker replaced since has none.
- `muructl debug logging` asks each worker, through the `logging_setup` debug operation, for the logging and warnings setup in force, reading only: every logger in the manager's dictionary with its level, effective level, propagate and disabled flags and handlers; for each handler its class, level, where it writes, its format string or formatter class and its filters, and nothing else from its settings, a URL's user information masked; the logging.disable level, logging.lastResort, whether warnings are captured, and warnings.filters in order. A level's origin is told from what Muru recorded: the levels its defaults set (`muru`), those `muructl logging level` set (`temporary`), either changed since (`changed since`), the root at Python's WARNING (`python`), else the application or a library. The text form shows the root and the loggers with something of their own unless --all, and one setup for workers that match. The bundle keeps each running release's as `config/logging-setup.json`.
- faulthandler is enabled in every worker with its output routed to the log collector, so a crash in a C extension leaves a Python traceback rather than nothing.

**Phase 2 interim.** The first slice (ADR 0025) builds the in-process mechanism: a control thread in the runtime library on a socket pair inherited at fork, the host relaying the daemon's requests, and faulthandler on SIGQUIT for a worker that cannot answer in time. Stacks are taken from inside until the PEP 768 reader is added for Python 3.14 and later.

**Scope and limits.** Every command is an admin-role operation (section 10.6), is recorded in the audit log, and works through the daemon's existing channels, so nothing listens anywhere new. Reading another process needs the right ptrace permissions: the same user suffices on Linux with the default ptrace scope, while macOS allows it only to root (ADR 0028), and in a container the host does the reading from inside. Status, stacks, tasks, inspect, logging levels and faulthandler arrive with the daemon in phase 2; profiling, tracing, memory tracing, attach, exec and the automatic captures follow in phase 3 with the soft timeouts and memory policy they build on (section 14.5).

- **Details fixed by the implementation.** A `Debug` reply is one message holding every worker's answer, so the admin client takes up to 256 MiB of it, rather than tonic's default of 4 MiB, and past that says what to narrow; the admin servers set no encoding limit. Profiling, tracing, memory and exec go the same way as the phase 2 commands, through the runtime's control thread (ADR 0025), so they work on every supported interpreter. An operation over a period (`profile`, `trace`, `memory` with `--trace`, and `exec`, which runs for as long as its code does) runs on a thread of its own the control thread starts for it, so the requests the control thread answers without the interpreter, and `stacks`, are still answered during the period; the host matches answers to requests by id, so they need not come in order, and the control connection is written a whole line at a time. A worker runs one of them at a time and refuses a second, answering at once that another is running; a profile the host reads from outside the worker (Linux, Python 3.15 and later) takes no thread of the worker and is not counted: `profile` samples `sys._current_frames()` from that thread every `--interval` (10 ms) for `--for` (10 s), leaving out the thread answering and the worker's main thread, which waits in the runtime, and returns collapsed stacks labelled `qualname (file:first line)` under the thread's name, which muructl merges across workers and writes heaviest first, with the busiest leaf functions on standard error; `trace` takes sys.monitoring's profiler tool id for PY_START, PY_RESUME, PY_RETURN, PY_YIELD and PY_UNWIND (Python 3.12 and later) and reports inclusive time and calls per function, refused when the requests on the worker's threads exceed half its threads, or those on its event loop half its concurrency, each side measured against its own slots (section 5.1), unless `--force`; `memory` reports rss, pss and uss as section 7.7 measures them, gc counts and statistics, and the commonest types among gc's objects, and with `--trace` compares tracemalloc snapshots at the start and end of the period by line, stopping tracemalloc after unless it was already on; `exec` parses the code, runs it in a fresh namespace with standard output and error captured, and returns its output and the repr of a final expression, refused unless the daemon's `[daemon]` table sets `debug_exec = true`. An operation over a period asks the host to wait its length plus 5 s and the daemon plus 15 s more. `profile`, `trace`, `memory` and `exec` are events (`debug.*`, exec at warning level with the first 200 characters of its code), which stand as the audit record until there is an audit log. The soft timeout's watchdog reads the overdue thread's innermost three frames, without opening source files, before it interrupts the thread, logs them, and sends the host a `request.soft_timeout` event naming the worker; for an ASGI request, whose task is cancelled, the event names no place. Before a hard-timeout kill the host asks the worker for its stacks, logs them and adds where the oldest request was to the `worker.timeout_killed` event, sending SIGQUIT only when the worker does not answer within a second; before a memory recycle it asks for the five commonest object types and adds them to `worker.recycled`. `breakpoint()` in a worker records where it stopped, raises `debug.breakpoint`, takes its request out of the soft and hard timeouts, and waits for an attach for 60 s or its `timeout` argument, then carries on with `debug.breakpoint_expired`; a `PYTHONBREAKPOINT` in the environment keeps its own hook. In a coroutine it holds the worker's event loop while it waits, as pdb does, and its request stays under the timeouts, since an ASGI request has no thread of its own to exempt. `muructl debug attach` carries the session line by line over the Debug operation (`attach`, `attach_io` and `detach`, with `breakpoints` listing those waiting), each line answered with what pdb wrote since and the session polled every 300 ms meanwhile; without `--worker` it takes the first worker with a breakpoint waiting. The session takes the oldest breakpoint waiting, or else starts a thread of its own; `continue` with no breakpoint left, `quit`, the end of input, an hour in all or ten minutes without a line end it, the operator's breakpoints cleared so the code goes on. A debugger runs code in the worker, so attach is refused unless `debug_exec = true`, as exec is; a session is `debug.attached` (warning) and `debug.detached`. Between an attach the worker accepts and its last session's `debug.detached`, the host leaves the worker out of the sockets it announces and pins it, recycling, the hard timeout, the memory limits and scale-in waiting meanwhile, so the debugged thread takes no request; `debug status` shows the worker as `debugging`. `debug status` shows each worker's state (`starting`, `ready`, `debugging`, `replacing` for one a fresh worker takes the place of, `retiring` for one scaled in), whether the edge routes to it, and what each side it has holds as of the moment it answers (issue 369): THREADS, the requests holding an application thread of how many there are, and THREAD-OLDEST, how long the longest has held one, a request holding its thread from the moment a pool thread picks it up whatever the timeouts make of it, so one at `breakpoint()` or streaming counts; LOOP and LOOP-OLDEST likewise for the requests on the event loop of its concurrency, accepted WebSockets left out of both; SYNC, for a worker with a loop, the threads running synchronous code of the threads that may, for the fullest of the pools such code runs on (section 6.6: the loop's own, anyio's and asgiref's shared thread, each in the answer as sync_pools), counted whether or not the request that made the call is still in flight, and SYNC-OLDEST the age of the oldest request with a call on the loop's pool or asgiref's thread. The worker's table records each such thread against the request while the call runs, so `debug stacks` names the request on each `muru-sync` thread. The host asks each worker (`slots`, answered by the runtime's control thread without the interpreter, as the bookkeeping is), and one that does not answer within a second is shown from its last report, which carries the same figures, marked stale; the hard timeout keeps using the report's age of the oldest request that is not exempt. The table shows the columns of the sides any worker of the release has, every header one word, and `--json` carries `state`, `routed`, `threads`, `loop` and `stale`. `--dap` listens on `--listen` (127.0.0.1:5678) for one IDE and then attaches with `dap`, which in the worker starts debugpy's adapter on a loopback port (`debugpy.listen`), once, debugpy staying in the worker for later sessions, refused when debugpy cannot be imported, and relays bytes between a connection to it and the session, base64 in `attach_io`'s `data` both ways, muructl sending what the IDE wrote with each request and polling as for pdb; a breakpoint waiting stops at its caller's next line once the IDE has sent configurationDone, and the IDE disconnecting, `detach`, or the session's limits close the connection, which the adapter takes as the end, letting the code go on. `profile --path PREFIX` samples only the threads serving requests whose path (with its query) starts with the prefix, looked up in the runtime's requests in flight at each sample, and `--requests N` ends the profile once N of them have finished, a request counting as finished when it is no longer in flight, so one shorter than the interval may go uncounted; ASGI requests, which have no thread of their own, are not sampled this way, and neither a header to choose requests by nor the options on `trace` are offered. `--format pstats` (with `--output`) writes the merged samples in pstats' marshal format, each function `(file, first line, qualified name)` with the file's base name, its calls the samples it appeared in, counted once per sample however often it recurs, its own time the samples with it as the leaf and its cumulative time the samples it appeared in, each sample worth one interval, and each caller likewise. On Python 3.15 and later the host reads its workers from outside with `_remote_debugging.RemoteUnwinder` (PEP 768) wherever the operating system lets it, which is Linux; macOS needs root, so there and on older interpreters the worker is asked as before (ADR 0028). Python 3.14's unwinder stops where C code called into Python, losing the frames above a builtin such as `breakpoint()` or a callback such as `sorted(key=...)`, and the runtime's own above the application, so on 3.14 the worker is asked, and a worker that does not answer in time is then read from outside, its stacks short but better than none, with faulthandler's dump in the log as well; the capture before a hard-timeout kill goes the same way. The first read the system refuses is logged and the host asks from then on. Read from outside are `stacks`, whose answer carries `outside`, each thread's source line taken from the host's linecache, and the capture before a hard-timeout kill, and `profile` without `--path` or `--requests`, which the host samples on a thread of its own, the main thread left out, each frame labelled by the line it was running rather than the function's first line. Each application thread of a WSGI pool waits for work inside a Python frame of the runtime's, `muru._pool.serve_jobs`, which calls back into the runtime for its whole life and runs no bytecode meanwhile, since the reader cannot start from a thread parked at its interpreter's base frame, which a thread the runtime made otherwise is while it waits; threads with no Python frames, or waiting in that frame, are left out of stacks and profiles whichever way they are read. Names and requests come from the runtime's `bookkeeping`, which its control thread answers without the interpreter: the requests in flight with the thread serving each, and the names of the threads that tell the runtime theirs, which are the application threads, the event loop's thread and the threads of the loop's pools for synchronous code and of a gRPC mount's pool. On Linux a thread read from outside is known by its TID, and a thread the runtime does not name is named by the kernel, to which `threading` gives each thread's name as it starts and when it renames itself on Python 3.14 and later, cut to 15 bytes: the host reads `/proc/<pid>/task/<tid>/comm` as soon as it has read the frames, and once for each thread over a profile, the main thread being the thread whose TID is the worker's pid, and a name equal to the process's, which a thread nothing names inherits from the one that started it, counting as none. A thread neither names is `MainThread` when its innermost frame is the host's, else `thread-IDENT` (ADR 0053). A worker whose bookkeeping does not come within a second is shown without them. `tasks`, profiles with `--path` or `--requests`, and the soft timeout's capture stay inside. `memory --snapshot` keeps a tracemalloc snapshot in each worker (10 frames, tracemalloc started when off), replacing one kept before, `--diff` compares the present with it by line, keeping it, and `--drop` lets it go and stops tracemalloc when `--snapshot` started it; a `--diff` with none kept is refused. A traced worker stays in the sockets the host announces, so the edge routes to it as to any other and the trace counts the requests it serves meanwhile.

Development mode shows tracebacks in error pages and the terminal, and supports --single for running the whole application in one process under a debugger (section 13.1). The attach command is for what --single cannot cover: a bug that only shows with forked workers or real traffic, or in the release itself.

## 11.8 Times on log lines

Every line and record gets a time when Muru first handles it, whether or not that time is shown; showing it is a choice each output makes (ADR 0043).

- **What the time is.** An access record's time is when the request arrived. A Python logging record in the json format carries the time it was created. Any other line carries the time it reached the process that tags it: the host's relay for worker output, and the writer of Muru's own lines for those. Durations beside a time come from the monotonic clock.
- **Two forms.** A record uses the full form, RFC 3339 in UTC with milliseconds and a `Z` (`2026-11-02T05:42:22.836Z`), which sorts as text and parses the same everywhere. The short form, a clock (`16:42:22.836`), is in local time, because a clock without a zone is read as the reader's own; it is used only on a terminal. A short clock in UTC is never shown.
- **The order.** A line with a time starts with it, then the tag, then the message: `2026-11-02T05:42:22.836Z muru.worker[0]: WARNING demo: warned`. Muru's own lines are written by one helper that puts the time, the tag and the message in one write, and the daemon's tracing output uses the same layout.

| Output | Application and Muru lines | Access lines |
| --- | --- | --- |
| Standard output and standard error of a long-running command (`muructl run`, `muructl serve`, `muructl daemon run`) | no time; `--timestamps`, or `[logs] timestamps = true`, puts the full form in front of every line | their own time first: the short clock on a terminal, the full form otherwise; the full form on every line with `--timestamps` |
| Files (a release's log, `edge.log`, `daemon.log`, and standard output or error redirected to a regular file) | always the full form in front | JSON lines (`access.log`, or `--access-log-file PATH` under `muructl run`) with the full form in `time` |
| journald | no time, since journald stamps each line | the record's time as a field |
| JSON records, to any output | a `time` field in the full form, never a prefix | the same |
| `muructl logs` | the full form shown; `--no-timestamps` hides it | the same |
| The dashboard | a time column with the short clock in the viewer's local time and the full form on hover | the same, in the requests table |

- **No time on standard output by default.** A person at a terminal is watching lines as they happen, and a container runtime, journald or a supervisor stamps every line it collects, so a second time would be noise; the access line keeps its time because it is part of the request's record, as in other servers' access logs. `--timestamps` is for a supervisor that stamps nothing.
- **Files always carry it.** A process tells a file from a terminal or a pipe by what its stream is, so the daemon's and the edge's files, a release's log and a command's output redirected to a file are all files. A file is read after the fact, by `grep` and `sort` as well as `muructl logs`, and a time not written there cannot be shown later, so there is no setting to leave it out. A reader that does not want it hides it. Everything Muru itself writes to such a stream goes through the helper, so the lines a daemon prints at start (its locations) and the edge's lines about draining are stamped like the rest, and the error a command exits with is written there as one of Muru's lines, `muru: error:` and the error with its causes on one line, rather than the multi-line form a terminal gets; the same holds under `--timestamps` and for JSON records. A panic in muructl, the daemon or the edge is reported by a hook in the same helper rather than the standard library's: `muru: panic: thread 'NAME' panicked at FILE:LINE:COL: MESSAGE`, then the note on how to ask for a backtrace (for the first panic only, as the standard library gives it) or, when `RUST_BACKTRACE` asks for one, one `muru: panic:` line for each frame, in the standard library's short form unless the variable is `full`, every line stamped where the stream is. In JSON it is one record of kind `panic` with `message`, `thread`, `location`, and `backtrace` as an array of frames or `note`. What the panic does next and the exit status it leads to are unchanged.
- **The dashboard's buffer keeps the time with each line**, as the access log's records do, rather than plain strings.
- **One output stream.** Under `muructl serve`, application, Muru and access lines all go to standard output, so they stay in order and a log collector does not treat every access line as an error for arriving on standard error.
- **Records a log collector keeps whole.** A collector splits records at newlines, so under `muructl serve --log-format json` each record is one line. A line of the application's output that is itself a JSON object, as Python logging's json format writes one (the default for Python logging under that flag), is the record, keeping its own `time`, with `kind` and `source` added, rather than a string inside another record. A traceback written to a stream arrives a line at a time; the host's relay gathers each source's traceback, from `Traceback (most recent call last):` to the exception's line with any chained exceptions, and writes it as one record, or as far as it got once nothing more has come for 200 ms. Every JSON line carries the pod's identity from the Downward API variables (`POD_NAME`, `POD_NAMESPACE`, `NODE_NAME` as `pod`, `namespace`, `node`) and OpenTelemetry's `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES` (`service`, `resource`) when they are set.

## 11.9 Diagnostics for triage

Three commands get the evidence for a problem out of Muru, each for a different reader (ADR 0058). All are under `muructl debug`, one word for each kind of output.

| Command | What it is | Who sees it |
| --- | --- | --- |
| `muructl debug report` | A short summary of the installation, printed as text, Markdown or JSON | Public, attached to a bug report on Muru (section 18.6) |
| `muructl debug bundle` | An archive of the whole system for a time window, made on request | The people who own the system |
| `muructl debug incident` | Evidence gathered automatically while a rule's condition holds | The people who own the system, and agents |

- **Names.** A *report* is a summary printed to standard output. A *bundle* is an archive file, and an incident exported writes the same layout, so one reader handles both. *Capture* stays for per-request records and for recorded traffic, and is used for nothing here. An *incident* is a stored record with a start and an end, produced by a *rule*. `TARGET` is `app` or `app@release` as for the other debug commands; `--format` and `--output` follow `muructl debug profile`; `prune`, `--keep`, `--older-than`, `--dry-run` and `--yes` follow `muructl logs prune`.
- **One collection.** What the commands collect is shared code: the facts about an installation are types of `muru_controller::diagnostics`, filled the same way whoever asks. A fact is read from the daemon's files where they hold it (the state store, opened read-only as the `muructl logs` commands open it, and the configuration file), and a running daemon is asked only for what it alone knows (the workers' states, what a worker has loaded), each question with a time limit of its own. A running daemon says in its status where its state, log and cache directories and its configuration file are, and they are read from there unless an option of the command names another place, since what the command's own environment resolves to may be another daemon's; with the daemon stopped the location options and the environment decide (section 13.8). A development run and `muructl serve` keep no files, so their admin socket is asked for everything. A part that cannot be collected is recorded with the reason in place of what it would have held, and collection carries on. The report is a safe subset of the collection.
- **The report.** `muructl debug report` holds Muru's version, the operating system, kernel and architecture; how Muru runs (`muructl run`, a user daemon, a system daemon or `muructl serve`), whether it is running, and whether in a container (the files a container runtime leaves at the root, the variables Kubernetes and systemd's container managers set, or the cgroup of process 1); every release with its state, interface, Python version and build and workers' states, and for a serving one the frameworks among the modules one worker has loaded, looked up from a fixed list so that no module of the application's own is named; the effective settings of the serving releases with the layer each came from (section 3.3), which for a run and a serve are the settings `--print-config` prints (section 13.1); what the daemon's configuration file sets; the events of the last 24 hours counted by type and level, and the ten most recent warnings and errors. With the daemon stopped a release has no workers and no detected interface, which only a running host knows.
- **Safe to post.** The report may be pasted into a public issue, so nothing in it identifies the system, and it is built once with its placeholders before any format is written, so text, Markdown and JSON say the same. Application names read `app1`, virtual hosts and the hosts of URLs `host1`, the machine `node`, users and groups `user1`, each value keeping its placeholder wherever it appears, replaced only as a word of its own. Muru's own directories read `<state-dir>`, `<run-dir>`, `<log-dir>`, `<cache-dir>` and `<daemon-config>` with what follows kept, since the layout below is Muru's; the home directory reads `~` and a path under it `~/<path1>`; any other absolute path reads `<path1>`, except the operating system's own (`/usr`, `/bin`, `/lib`, `/opt/homebrew` and the like), which say nothing about an installation. An address other than loopback and the unspecified address reads `<address1>`, and a URL keeps its scheme and port and loses its user, password, path and query. An entry point's or a hooks module reads `<module1>` and a package it is in `<package1>`, for every release's entry point and wherever a text names one, so that the sentence of a release that failed to import its application does not. A setting's value is shown only when its key is on a list of those known to be numbers, switches, sizes, durations, addresses or paths; any other reads `<set>`, so a setting added later stays out until it is listed, and one whose name marks a secret reads `<redacted>`. Of the daemon's file, the tables that configure the daemon itself (`daemon`, `tools`, `listener`, `limits`, `proxy`, `compression`, `logs`, `shutdown`, `metrics`, `dashboard`) are listed setting by setting and every other table only by how many entries it has. An event's sentence is given with the same replacements, and left out for the events that quote a request, a command or the application's code (`request.*`, `command.*`, `debug.exec` and the breakpoint events). There are no log lines, access log lines, request data, client addresses or environment variables at all. Nothing is hidden or encoded: the person reads the report before posting it, and its last line says how many values of each kind were replaced.
- **Markdown.** `--format markdown` uses only CommonMark and pipe tables, with no HTML, so it renders the same on any tracker. Every value from the system is in a code span whose delimiter is longer than any run of backticks in the value, or in a fenced block whose fence is longer than any in its lines, so no value is read as markup and no `@name` or `#123` in one notifies anyone or links to an issue. A pipe in a table cell is written `\|`; a value with an odd number of backslashes before a pipe is given one more, since a table reads two backslashes and a pipe as the end of the cell.
- **The window.** A bundle and an incident cover a period, from an instant up to when they were asked for. A log can be several gigabytes and the window is usually its last hour, so where the window starts in a log is found from the times its lines carry (section 11.8: the full time in front of a line of a file, the `time` of a JSON record, or the bracketed time of the combined format), by halving the file: each step looks only as far as the next line with a time, at most 256 KiB, and once the place is within 64 KiB the lines are read one after another. A line without a time, as the second line of a traceback, belongs with the one before it; a stretch longer than is looked through is taken with what came before; and a run of NUL bytes, as a file cut in place under a writer that kept its offset starts with, is older than anything. Only the window is then read from the file.
- **The bundle.** `muructl debug bundle [TARGET] [--since 1h] [--output FILE|-] [--dry-run]` writes one `.tar.gz` of the system for a window. Unlike the report it keeps real log lines, client addresses and query strings, because it does not leave the people who own the system; it still never holds secret values, environment values beyond what `debug inspect` shows, or request and response bodies, since an archive gets copied to laptops and attached to tickets.
- **The archive's layout.** Every part is under one directory named for the bundle (`muru-bundle-YYYYMMDD-HHMMSS`), each member with mode 0600, and the layout is fixed in `muru_controller::diagnostics::archive` so that an incident exported is read the same way: `manifest.json`; `installation.json` (the report's facts without its placeholders, with the daemon's locations); `config/`; `events.jsonl` (every event of the window, a JSON object a line); `logs/` (by the names in the log directory); `live/`; `figures/`; `host/`; `failures/`; and `incidents/`, where each incident of the window goes in a directory named by its id and laid out as an archive of its own. The manifest is the last member, since it lists what the stream before it held: the layout's version, the kind, when and by which version it was made, the node, the target, the window, how Muru runs, how the making was recorded, what a bundle never holds, and every part with whether it was collected, its size before compression, and why not when it was not.
- **On a system in trouble.** A bundle is made when things are going wrong, so it must not make them worse. It reads files instead of asking the daemon wherever a file holds the fact; it lowers its own scheduling priority and compresses at the fastest setting; and it writes the archive as a stream, part by part, holding nothing in memory or on disk beside it, which is also what lets `--output -` send it through `ssh` or `kubectl exec` when the disk is the problem. A part whose size is known before it is read, a stretch of a log, is copied straight in; if its source ends early or fails, the member is made up with line ends and says so, so that only a failure to write the archive itself ends the command, in which case the partial file is removed. Each question of the daemon has a time limit of its own, and a part that cannot be collected is recorded in the manifest and the rest carries on: partial results are normal and the command succeeds. It works with the daemon stopped, from the files, and under `muructl run` and `muructl serve`, which are asked for everything.
- **Where it is written.** A file is created with `O_EXCL` and mode 0600, so it is readable by its owner alone from the start and an existing file, which would keep its own mode, is refused. Before a file is written the command plans the bundle (the same collection against an archive that only lists its parts, asking nothing of the workers), takes what is compressed already at its size and text at a quarter of its own, and refuses with what it needs when the file system has less free. `--dry-run` prints that plan. On completion the command says where the archive is, how many parts it holds, what it could not collect, and that it holds production data; with `--output -` it says so on standard error.
- **Recorded.** Each bundle is recorded as the debug operations are: the command calls `NoteBundle` before it collects, and the daemon raises `debug.bundle` (notice) on the application or release the bundle is limited to, else on `daemon`, saying how far back it reaches. A development run and `muructl serve` print the line. With nothing running there is nothing to record it, and the manifest says so; a dry run records nothing.
- **The bundle's configuration.** `config/` holds what is in force when the bundle is made. With the state store in reach, read without the daemon: `releases/APP@RELEASE.json` for every release, not only the serving one, with its effective settings and the layer of each (section 3.3) and its whole specification; `effective.toml`, the document `muructl config show --effective` writes; and `in-force.json`, what is in force outside configuration (each rollout and where it stands, scale pins, the applications and virtual hosts in maintenance mode, each overlay's state). Without the store (a development run, `muructl serve`, or a store the user may not read) `effective.toml` is what `config show --effective` prints, asked of what runs. `daemon.toml` is the daemon's own file. `access-log-overrides.json` and `routing-snapshot.json` (the snapshot version the edge routes by, from the `muru_snapshot_version` metric, which an access log record's `snapshot` names) are asked of the running daemon. `changes.jsonl` is the window's events that change configuration (`config.applied`, `config.reloaded`, `traffic.*`, `traffic_policy.*`, `route.*`, `maintenance.changed`, `access_log.*`, `release.created`, `release.removed`, `rollout.*`, `overlay.activated`, `overlay.ended`, `overlay.promoted`, `schedule.*`, `client_class.list_reloaded`, `deploy.freeze_overridden`), and the manifest's `configuration_changed` says plainly whether there were any, since the rest of `config/` is as it was when the bundle was made. `logger-levels.json` is what each running release's workers answer when asked which logger levels `muructl logging level` has changed, keyed by app@release. Muru keeps only the routing snapshot in force, so the manifest lists the earlier snapshots as not collected, with that reason.
- **What a bundle masks.** A variable a release declares with its value (section 10.8) is masked as `debug inspect` masks a worker's environment (section 11.7): `***` under a name that looks like a secret's, and the password of a URL alone. That goes for a release's specification and for the `env` tables of the effective document, which an export writes with their values. A secret from a store is only ever its store and key. In the daemon's file a setting is masked by its key read word by word, since settings are named in words: `secret`, `token`, `password`, `credential`, `auth` or `dsn` anywhere, or `key` at the end after another word, as `signing_key`; a `key` alone and `hash_key` name what something is keyed by and stay.
- **The bundle's logs.** `logs/` holds the logs of the window by their names in the log directory (section 11.3): `access.log`, `edge.log`, `daemon.log`, the files virtual hosts name, and `apps/APP/RELEASE.log`. A live log is taken from where the window starts in it, found as above, to its end as it was when it was opened, and the file stays open meanwhile so a rotation under it changes nothing. An archive the rotation left is included when it was last written in the window, which its modification time says (the last line for a plain one, the end of compression for a compressed one): a plain archive gives its lines of the window, and a compressed one is included whole and still compressed, since the window cannot be found in it without decompressing all of it, and compressing it again would cost a system that may have nothing to spare. The directory is the one the running daemon names (ListLogs), else where the location options put it. A development run and `muructl serve` write no files (section 13.8), so they are asked through TailLogs for the lines they keep in memory, and the lines of the window among them are the part.
- **A target and `--scrub`.** Both pass a log's lines through on the way into the archive instead of copying the stretch. With a target, another application's release logs are left out, and of the access log's JSON records only those that name the target are kept, found by their `"app"` and `"release"` fields as written, which cannot occur inside another string since a quote in one is escaped; a record in the combined format names no application and stays. `--scrub` replaces client addresses with `<address1>` and so on, the same one for the same address so that a client can still be followed, loopback and the unspecified address kept, and cuts the query string from each request target and URL: in every string of a JSON record and of an event, and in any other line, which is free text, wherever something has the shape of either. Since a tar member's size is written before its bytes, a stretch whose lines are passed through is read twice, once to learn the size and once to write, which gives the same bytes both times because the stretch is fixed and the placeholders once given do not change; nothing is held in memory or written to disk. A compressed archive is decompressed for it and goes in under its name without the suffix. A plan gives the size going in.
- **The bundle's live state and figures.** `live/` holds what the workers are doing as the bundle is made, for each release of the target that has workers: `status.json`, `tasks.json`, and the stacks three times, two seconds apart, as `stacks-1.json` to `stacks-3.json`, since one sample cannot tell a thread that is stuck from one that is busy. Each is the Debug operation's answer as the command's own `--json` prints it, asked with the time limit every question has, so a hung worker costs that limit and its part, and the other releases and samples are still taken. The first stacks are asked for before anything else is asked of the workers. `requests.json` and `websockets.json` are the edge's lists (ListRequests and ListWebSockets), up to a thousand entries each. `figures/` holds `metrics.txt`, the Prometheus text a scrape reads, which carries the garbage collection figures (`muru_gc_*`, section 11.1), and for a daemon `scaling/APP@RELEASE.json`, each group's scaling diagnosis (GetScaleStatus). The history the dashboard's charts draw is held in memory and served only by the dashboard, to a session under a daemon (ADR 0030), so it is not in a bundle and the manifest says so. A plan lists these parts without asking: for a daemon, of the releases the state store has in a state a host runs in.
- **The bundle's application and host.** `host/host.json` is the machine as `muru_controller::diagnostics::facts::Host` reads it: the kernel (`uname`), the CPUs the command may run on, the load averages, the memory and on Linux how much is available (`MemAvailable`), the soft and hard limits on open files of the command, the size and room of the file system of each of Muru's directories (`statvfs`), and on Linux the limits the kernel holds the daemon's and the edge's processes to (`/proc/PID/limits`) and the cgroup v2 limits of the daemon's cgroup, else the command's own, which in a container is the same (section 13.9). What Linux alone tells is absent elsewhere, not guessed. For each release of the target, `host/APP@RELEASE/packages.txt` lists the distributions in the `site-packages` beside its interpreter, from the names of their `.dist-info` directories, so nothing is run and no file opened, and the lock files of its source that are there (`uv.lock`, `pylock.toml`, `requirements.txt`, `poetry.lock`, `pdm.lock`, `Pipfile.lock`, each up to 4 MiB) are copied with the password of any URL in them masked; the interpreter and the source come from the state store, so this works with the daemon stopped, and for a development run from the interpreter a worker names and the run's project directory. `host/APP@RELEASE/inspect.json` is `debug inspect` of the release's workers, without `--env`: the interpreter and build, `sys.path`, the loaded modules with versions, the threads and descriptors, and the environment as section 11.7 shows it.
- **The bundle's past failures.** `failures/events.jsonl` is every event still kept, from before the window too, that records something going wrong: `request.soft_timeout`, `request.past_deadline`, `worker.timeout_killed`, `worker.oom_killed`, `worker.recycled`, `worker.exited`, `worker.loop_stalled`, `worker.gil_stalled`, `worker.restarted`, `release.failed`, `release.import_failed`, `release.build_failed`, `host.exited`, `server.exited`, `server.failed`, `edge.failed`, `preload.fell_back` and `memory.leak_suspected`. The automatic captures of section 11.7 are in the events' sentences, and the stacks a worker dumped through faulthandler before it was killed are in its release's log, under `logs/`. The incidents of the window go under `incidents/` once Muru records them.
- **Only when asked for.** Two parts cost the workers something and are opt-in: `--memory` runs `debug memory` on each release's workers, which holds each interpreter while it counts objects, into `live/APP@RELEASE/memory.json`; `--profile DURATION` profiles every release's workers over the same period, the releases asked at once so the bundle takes the period and not a period each, into `live/APP@RELEASE/profile.collapsed`, the workers' collapsed stacks merged heaviest first. They are asked for after the stacks have been sampled, and each is recorded as the debug operation it is as well as in the bundle's event, which names what was asked for.
